# Deploy

## Vercel

The console and admin portal are separate Vercel projects, deployed by the
repository's GitHub Actions workflow:

| App | Project Root Directory |
| --- | --- |
| `sites/net.alloydb.console` | repository root (root `vercel.json`) |
| `apps/backend` | `apps/backend` |

Set the database, auth, and optional integration variables in every project,
plus that app's own public URL (`NEXT_PUBLIC_APP_URL`). Point each site's
domain at its project; the domain must match
`domain` in the site's `src/site.config.ts`.

Stripe webhooks and scheduled billing work run on the admin portal:
use `https://<admin-domain>/api/webhooks/stripe` as the Stripe webhook URL
and sync Inngest with `https://<admin-domain>/api/inngest`.

## Control-plane and data-plane services

The Vercel workflow deploys the two Next.js apps. The control-plane and
data-plane container images are built separately by
`.github/workflows/images.yml` and run in the Kubernetes environment. The
control-plane and data-plane rollout is handled separately from the Vercel
workflow. The root Next.js `Dockerfile` does not build the control-plane service.

## Next.js app containers

The repository includes a `Dockerfile` that builds one app per image; choose
it with `--build-arg APP_DIR=… --build-arg APP_PACKAGE=… --build-arg PORT=…`
(the defaults build the AlloyDB console). Provide runtime environment variables to the
container and expose the application port used by the deployment. Run
the same database migration commands separately before serving traffic.

## After deployment

On each site, check `/status`, `/robots.txt`, the OAuth discovery documents,
and `/mcp` with the intended authentication state. On the admin portal, check
that `/login` loads and that admin pages redirect there when signed out. Do not use live secrets in smoke-test logs
or documentation examples.
