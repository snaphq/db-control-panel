# Run a referral program

The starter includes a first-party referral program. Eligible users get a
unique code, share it, and receive a fixed credit when the referred
organization starts paying. Rewards are issued as Stripe customer balance
credits that reduce future invoices. There is no cash payout, percentage
commission, or affiliate/partner tracking.

## Before you start

- `DATABASE_URL` and Stripe keys are set in `.env.local`.
- The Stripe webhook endpoint is configured (`bun run setup:stripe`), because
  referral state changes come from invoice and subscription events.
- Plan tiers exist. `bun run db:seed:billing` seeds the default tiers
  (`free`, `tier1`, `tier2`, `tier3`) and a disabled `referral_config` row.
  The config row is also created on demand with the same defaults.

## Configure rewards

Run the interactive wizard:

```bash
bun run setup:referral
```

Or edit the same settings in the admin UI at `/adminx/referrals` under
**Settings**.

| Setting | Default | Purpose |
| --- | --- | --- |
| `enabled` | `false` | Master switch for the program. |
| `referrerCreditAmount` | `1000` | Cents credited to the referring user ($10.00). |
| `refereeCreditAmount` | `500` | Cents credited to the new user's organization ($5.00). |
| `currency` | `usd` | ISO 4217 currency code. |
| `minPlanTier` | `tier1` | Minimum plan tier key required to create a code; blank allows every tier. |
| `autoApply` | `false` | Apply credit grants automatically instead of requiring admin approval. |
| `approvalWindowDays` | `30` | Days after the first payment before a referral is marked converted. |

## How the flow works

1. A user on a qualifying plan opens **Referrals** in the dashboard sidebar
   (`/dashboard/<workspaceSlug>/~/referrals`) and copies their share link.
2. The share link is `/r/<code>`. Opening it records a referral intent, sets a
   `referral_code` HTTP-only cookie for 30 days, and redirects to the landing
   page with `?ref=<code>`, where the pricing section shows the referral credit
   banner. Invalid or deactivated codes redirect without setting the cookie.
3. When the visitor signs up with email, the sign-up route reads the cookie and
   creates the referral, then deletes the cookie. Self-referrals are rejected
   and each user can be referred only once. The referral is linked to the new
   organization when it is created.
4. Stripe events advance the referral status:
   - checkout/subscription created → `trial`
   - first successful invoice → `refund_period`, and referrer and referee
     credit grants are recorded (applied immediately when `autoApply` is on)
   - subscription deleted before conversion → `cancelled`
5. A daily Inngest job (`billing-referral-window`, 01:00 UTC) marks referrals
   `converted` once `approvalWindowDays` have passed since the first payment.

Both grants are issued as Stripe customer balance credits: the referrer's
credit lands on their own organization's customer, and the referee's credit
lands on the referred organization's customer. Every transition is written to
`referral_lifecycle_log`, and credit grants are idempotent per invoice and
recipient role so duplicate webhook deliveries cannot double-credit.

## Admin operations

`/adminx/referrals` has four tabs:

- **Codes** — search codes and activate or deactivate them.
- **Referrals** — track each referrer/referee pair and its status.
- **Grants** — approve or reject pending credits and review applied ones.
- **Settings** — the reward configuration above.

Metrics on the same page show referral totals, conversions, pending grants, and
applied credits.

## Current limitations

- Attribution happens in the email sign-up route; OAuth sign-ups are not
  attributed.
- Rewards are Stripe customer balance credits only. There is no cash payout,
  revenue-share percentage, affiliate account, or partner commission flow, and
  no Stripe Connect or external affiliate service is wired in.
