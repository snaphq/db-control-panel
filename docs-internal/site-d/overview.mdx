# com.site-d

`sites/com.site-d` is the fourth tenant site and the second that does **not**
consume the shared `@repo/site-kit` route tree. It runs Astro 7 in
`output: "server"` mode with the Vercel adapter, React 19 islands for the
auth forms and menu toggle, and Tailwind 4 through the Vite plugin, while
sharing the monorepo's single `DATABASE_URL` and owning its own tenant.

| | net.alloydb.console / com.site-b | com.site-c | com.site-d |
| --- | --- | --- | --- |
| Framework | Next.js 16 App Router | SolidStart 2 + Vite 8 | Astro 7 |
| Shared routes | `@repo/site-kit` | none, owns `src/routes` | none, owns `src/pages` |
| API | Next route handlers | Hono, mounted at `/api` | Astro API route at `/api/auth/*` |
| Styling | Tailwind 4 + `@repo/react-ui` | Tailwind 4 + Solid primitives | Tailwind 4 + React islands |
| Node | 22 | **24+** | **22.12+** (Astro 7 requirement) |
| Deploy output | `.next` | Nitro (`.output` locally) | `.vercel/output` via `@astrojs/vercel` |

## Why it does not use site-kit

Same decision as [com.site-c](/site-c/overview), and the same
mechanism: **do not list `@repo/site-kit` in the site's `dependencies`**.
`scripts/sync-site-routes.ts` selects sites by exactly that dependency, so its
absence is a complete opt-out. The `StandaloneSiteConfig` type import in
`src/site.config.ts` is type-only and resolves through a tsconfig path
mapping.

Astro's routes live in `src/pages` and its pages are `.astro` files with
server-side frontmatter, so no Next.js route tree can be re-exported into it.
Marketing pages render server-side per request; React components opt into
client hydration with `client:load` / `client:visible` islands.

## Tenant resolution

One guard in `src/middleware.ts` runs on **every** request:

1. Resolve the tenant with `resolveTenantFromHost` from `@repo/database`.
2. If it does not resolve, return **404**. There is no default fallback. This
   mirrors the guards on the other sites.
3. Otherwise store the tenant on `context.locals.tenant` (typed through the
   `App.Locals` augmentation in `src/env.d.ts`) and continue. Pages, the
   dashboard, and the auth mount read it from there and never accept a tenant
   from the client.

Locally, `.env.development` pins `SITE_TENANT_ID=site-d`, which
`getLocalTenantId()` reads for local hosts. Test alongside the other sites
through `com-site-d.localhost:8804`; browsers share cookies across localhost
ports, so the host-prefixed form matters when several sites run at once.

Astro's Vite dev server rejects unrecognized Host values with its own 403
before the guard runs (`vite.server.allowedHosts` allows only localhost and
`.localhost` in this site). That is fail-closed and dev-only; in production
every Host reaches the app and the guard is the boundary.

## Auth

`src/pages/api/auth/[...all].ts` mounts Better Auth for every method under
`/api/auth/*` by calling `handleAuth` in `src/server/auth.ts`, which is the
same wiring com.site-c uses:

- `getBetterAuthServer({ cookieDelivery: "response" })` — Astro, like
  SolidStart, returns the Response as-is, so Better Auth's `nextCookies`
  plugin (a Next-only `Set-Cookie` re-applier) is omitted rather than unused.
- The handler runs inside `runWithAuthTenantContext` with the tenant from
  `context.locals`, which `withTenantBoundAuthAdapter` requires for every
  tenant-bound read and write.
- `resource` is the tenant's own `/mcp` URL from
  `resourceUrlForRequest` in `@repo/core`.

Session checks in pages call `getSessionFromRequest` in `src/server/session.ts`,
which delegates to `getSession` in `@repo/auth/server` — it re-resolves the
tenant from the Host header and rejects cross-tenant sessions, so the result
is already scoped to `locals.tenant`.

`/dashboard/**` redirects anonymous visitors to `/dashboard/login`; the sign-in
and sign-up pages redirect signed-in visitors back to `/dashboard`. The forms
are React islands posting JSON to `/api/auth/sign-in/email` and
`/api/auth/sign-up/email`; the browser reloads after success so the
server-rendered pages pick up the session cookie.

The dashboard read models in `src/server/account.ts` take the resolved
`tenantId` plus the session's `userId` and never a client-supplied parameter.
They read only existing platform tables (`user`, `session`, `member`,
`organization`); no site-specific migration exists.

## Astro-specific integration notes

Three things bite in Astro that Next.js handles automatically, all handled in
`astro.config.mjs`:

- **Vite does not populate `process.env`.** Astro loads `.env*` files into
  `import.meta.env` only. The config calls `loadEnv` with an empty prefix and
  copies into `process.env` without overwriting real environment variables,
  so `DATABASE_URL` (read from `process.env` by `@repo/database`) and the
  `SITE_TENANT_ID` pin both work. Same fix as com.site-c's `vite.config.ts`.
- **`server-only` breaks SSR.** `@repo/auth/server` imports React's
  `server-only` marker, whose default entry throws outside a react-server
  build. Astro never sets that condition, so `vite.resolve.alias` points the
  marker at `src/shims/server-only.ts`, an empty module.
- **The middleware filename is fixed.** Astro requires `src/middleware.ts`;
  there is no setting to rename it. `scripts/check-no-middleware.ts` (the
  Next.js 16 middleware→proxy rule) exempts exactly `sites/*/src/middleware.ts`.

`tsconfig.json` extends the root config with `jsx: "react-jsx"` for the React
islands and maps `~/*` plus the `@repo/*` package paths. Biome formats the
`.astro` files too; the generated `.astro/` directory is ignored in the root
`biome.json`.

## Deploy

Vercel only. `vercel.json` sets `installCommand`/`buildCommand` to install and
build through the monorepo root with a turbo filter, and deliberately sets
neither `framework` nor `outputDirectory` — Vercel detects Astro from the site
manifest, and `@astrojs/vercel` emits `.vercel/output`.

`astro build` needs no network access and no site-specific secrets beyond the
shared `DATABASE_URL` at runtime.

The deploy matrix rows (`deploy-vercel.yml` and `deploy-vercel-preview.yml`)
carry `project_name: 'starter-astro-stack'` and `node_version: '22'` — Astro 7
requires Node ≥ 22.12, which the 22 line satisfies, so unlike site-c this row
did not need Node 24. The rows skip until the Vercel
project exists and its id is set with `set-vercel-projects.ts`.

## Tests

`bun run test` in the site runs Vitest; no suite needs a database:

- `src/config.test.ts` — the seeded identity fields (standalone stack, tenant
  `site-d`) and that navigation stays inside the site.
- `src/middleware.test.ts` — cross-site isolation: unknown host 404s, a
  missing Host header 404s, a resolved host binds its own tenant to locals,
  another site's host binds that site's tenant, and a `?host=` query
  parameter cannot smuggle a tenant past the guard. Mocks `@repo/database`
  with a host-to-tenant map, following
  `packages/core/src/tenant-isolation.test.ts`.
- `src/server/auth.test.ts` — the auth mount delegates the request to the
  shared Better Auth handler and wraps it in this tenant's auth context with
  the tenant's `/mcp` resource.
- `src/server/account.test.ts` — the read models bind the resolved tenant and
  the session user into their WHERE clauses, join through `member` for
  organizations, and return empty rather than throwing on a fresh account.
