# Control plane

`apps/control-plane` replaces the closed-source part of Neon's cloud and the
Turso platform API. It is one TypeScript codebase run in four modes (see
[Platform architecture](/platform/architecture)). The console never talks to
the data plane directly; it calls this service's API.

## Stack

- Node 22 at runtime (Bun is used only for installs and scripts), ES modules,
  TypeScript compiled with `tsc` into `dist/`.
- Hono with `@hono/node-server` for HTTP, Zod for request and env
  validation, Drizzle ORM with the `postgres` driver, pg-boss for the
  operations queue, `@kubernetes/client-node` for pods and routes, and
  `node:crypto` for Ed25519 and SCRAM (no extra crypto dependency).
- Vitest for unit tests of every pure module. Files stay under 600 lines.

## Source layout

```text
apps/control-plane/src/
  index.ts              mode switch (ALLOYDB_MODE)
  config.ts             env schema
  db/                   Drizzle schema, client, migrations
  crypto/               Ed25519 JWT signing and verifying, SCRAM-SHA-256 secrets,
                        AES-256-GCM sealing of stored credentials, ids
  k8s/                  kube clients and the pod API the compute runtime uses
  neon/                 storage-controller client, compute spec builder and
                        service, compute pod manifest, compute_ctl client,
                        compute runtime (wake, reconfigure, suspend), idle
                        suspend, safekeeper and pageserver registration, the
                        NeonStore (Drizzle and in-memory), steps/ (one plan
                        per Neon operation action)
  libsql/               sqld admin client, namespace naming, placement, token
                        minting, Service/EndpointSlice/IngressRoute builders,
                        node sync from Kubernetes, the libSQL store, steps
  data-api/             PostgREST bootstrap SQL and runner, sidecar provider,
                        platform JWT key, enable/disable steps, gateway
                        (routing, CORS, streaming proxy)
  modes/                api, neon-glue, worker, data-api-gateway servers; the
                        /v1 route files (api-*.ts)
  operations/           operation runner, queue, step registry
packages/control-plane-contract/
                        zod schemas and types of the public API, shared with
                        the console (`@repo/control-plane-contract`)
```

The contract package builds to `dist/` for the Node runtime; its `types`
condition points at the TypeScript source, and the control plane's tests alias
the source, so tests need no prior build. `bun run --filter @repo/control-plane
build` builds the contract first. The runtime image must therefore also carry
`packages/control-plane-contract` (its `dist` and `package.json`), because
`node_modules/@repo/control-plane-contract` is a workspace symlink.

## Data model

Database `control_plane`. Ids are prefixed strings generated by the control
plane (`proj_`, `br_`, `ep_`, …) except Neon tenant and timeline ids, which
are 32-hex values as Neon requires.

| Table | Key columns |
| --- | --- |
| `neon_project` | id, console_project_id, console_org_id, name, tenant_id, pg_version, history_retention_seconds, allowed_ips (jsonb CIDR list, null = unrestricted), data_api_jwks (public JWKS of the platform key), data_api_signing_key_enc (sealed private key), data_api_custom_jwks (keys the project brought; wins when set), created_at, deleted_at |
| `branch` | id, project_id, name, timeline_id, parent_branch_id, parent_lsn, safekeepers (jsonb: generation + `[{id, hostname}]`), authenticator_password_enc (sealed), is_default, deleted_at |
| `endpoint` | id (`ep-<word>-<word>-<n>`), branch_id, type (`read_write`, `read_only`), compute_size, suspend_timeout_seconds, state (`idle`, `starting`, `running`, `suspending`), pod_name, pod_ip, last_active_at, deleted_at |
| `role` | id, branch_id, name, scram_secret, password_enc (the password sealed with `ALLOYDB_DATA_KEY`; never plaintext) |
| `database` | id, branch_id, name, owner_role, data_api_enabled, data_api_index (sidecar position, 0-49, never reused within a branch) |
| `libsql_database` | id, console_org_id, console_project_id, name, namespace (`<name>-<team>`), node_id, state (`creating`, `active`, `deleting`), size_limit_bytes, created_at, deleted_at |
| `node` | id (`ALLOYDB_NODE_ID`), name, tailscale_ip, zone, roles, capacity (jsonb: `ready`, optional `libsqlMaxDatabases`), registered_pageserver, registered_safekeepers |
| `operation` | id, console_project_id, console_org_id, target_type, target_id, action, status (`scheduling`, `running`, `finished`, `failed`, `cancelled`), failures_count, error, params (jsonb), progress (jsonb: completed steps and their outputs), created_at, updated_at, finished_at |
| `usage_event` | id, project_id, kind, value, idempotency_key (unique), recorded_at |

Constraints worth knowing:

- Live rows are unique by partial index: one live `neon_project` per
  `console_project_id`, one live branch name per project, one default branch
  per project. A deleted project frees its console project for a new one.
- `operation` has a partial unique index on `console_project_id` where status
  is `scheduling` or `running`: the database, not the application check,
  guarantees one active operation per console project.
- Soft deletes (`deleted_at`) keep rows for the worker's cleanup steps; the
  console API never returns them.
- `operation.console_org_id` is null only for rows written before migration
  `0001`; reads require the caller's organization and project to match.
- `node.registered_safekeepers` is not set: safekeepers are pods, not nodes,
  and are registered by id (below). The `node` table is filled by two loops:
  pageserver discovery (from the storage controller) and the node sync (from
  Kubernetes Node labels, below), which owns `roles` and `capacity.ready`.
- A live libSQL namespace is unique across the platform (partial unique
  index); a deleted row frees it.
- The database never holds a password in the clear. `role.password_enc`,
  `branch.authenticator_password_enc` and `neon_project.data_api_signing_key_enc`
  are AES-256-GCM values (`v1.<iv>.<tag>.<ciphertext>`) bound to what they are
  through the GCM additional data (`role-password:<name>`,
  `data-api-authenticator-password`, `data-api-signing-key`), so a value copied
  into another place does not open. Roles created before migration `0002` have
  no sealed password; resetting it fills it in.

The console stores only its own `project.id` and receives these ids back.

## Operations

Mutations write desired state and an `operation` row in one transaction,
enqueue a pg-boss job, and return `202` with the operation. A project with an
operation in `scheduling` or `running` rejects new mutations with `423`.
Every step is idempotent and safe to retry; the runner stores each step's
output on the operation row and a retry resumes after the last finished step.
Actions:

`project.create`, `project.delete`, `branch.create`, `branch.delete`,
`endpoint.start`, `endpoint.suspend`, `endpoint.update`,
`role.reset_password`, `database.create`, `database.delete`,
`data_api.enable`, `data_api.disable`, `libsql.create`, `libsql.delete`,
`libsql.fork`.

The plans, with the Data API and libSQL actions at the end:

| Action | Steps | Written by the request, in the same transaction |
| --- | --- | --- |
| `project.create` | `tenant` (create tenant), `timeline` (root timeline, store safekeepers) | project, default branch `main`, endpoint, role `neondb_owner`, database `neondb` |
| `project.delete` | `computes` (suspend every endpoint), `tenant` (delete tenant) | `deleted_at` on the project, its branches and endpoints |
| `branch.create` | `timeline` (fork parent at `parent_lsn`, store safekeepers and the fork LSN) | branch, copies of the parent's roles and databases, optional endpoint |
| `branch.delete` | `computes`, `timeline` (delete timeline) | `deleted_at` on the branch and its endpoints |
| `endpoint.start` | `wake` | none |
| `endpoint.suspend` | `suspend` | none, or `deleted_at` when the endpoint is being deleted |
| `endpoint.update` | `stop` (only if the size changed), `apply` (start again, or push the spec) | new size and timeout, or the new endpoint row when one is created |
| `role.reset_password` | `apply` (push the spec to running computes) | new role row, or a new SCRAM secret |
| `database.create` | `apply` | database row |
| `database.delete` | `drop` (wake a compute, push the spec with a `delete_db` operation) | row removed |
| `data_api.enable` | `wake`, `bootstrap` (SQL as the owner), `restart` (the sidecar joins the pod) | `data_api_enabled`, `data_api_index`; the branch's authenticator password and the project's platform key when missing. With `targetType` `project` (new JWKS) only `restart` acts: it restarts the running computes that serve a Data API |
| `data_api.disable` | `restart` (running computes lose the sidecar) | `data_api_enabled = false`; the index stays reserved |
| `libsql.create` | `create.namespace` (admin API), `service`, `route`, `activate` | `libsql_database` row in state `creating` |
| `libsql.fork` | `fork.namespace`, then the same `service`, `route`, `activate` | the new row, on the source's node |
| `libsql.delete` | `delete.route`, `delete.namespace` | `deleted_at` and state `deleting`; params `keepBackup` |

Some API calls reuse a plan on purpose, so the action list stays small:
creating a role runs `role.reset_password`, creating or deleting an endpoint
runs `endpoint.update` or `endpoint.suspend` (the operation's `params` say
which). Soft-deleted rows stay readable by the worker until its cleanup steps
finish.

Roles and databases are applied through the compute spec, not SQL.
compute_ctl creates missing roles and databases, alters a role whose SCRAM
secret differs, and drops databases named in `delta_operations` on every spec
it applies (`compute_tools/src/spec_apply.rs`, phases `CreateAndAlterRoles`,
`RenameAndDeleteDatabases`, `CreateAndAlterDatabases`). That keeps one source
of truth, needs no superuser connection from the control plane, and means an
idle endpoint picks the change up on its next start. A dropped database whose
branch has no `read_write` endpoint stays in the timeline until one exists.
The Data API roles are the one exception: they are created with SQL (see
[Data API](#data-api)).

## Neon flows

**Create project.** `POST /v1/tenant` on the storage controller with
`{new_tenant_id, pitr_interval}`, then `POST /v1/tenant/:id/timeline` with
`{new_timeline_id, pg_version: 17}`. The response's `safekeepers` field
(present because of `--timelines-onto-safekeepers`) is stored on the branch;
a response without it fails the step. Re-sending either request is safe: the
controller treats the same tenant and timeline ids as a retry. The endpoint
starts idle; the first connection starts it, and compute_ctl then creates the
role and database from the spec.

**Create branch.** `POST /v1/tenant/:id/timeline` with `{new_timeline_id,
ancestor_timeline_id, ancestor_start_lsn?}`. Without an LSN the branch forks
at the parent's latest LSN and the response's `ancestor_lsn` is recorded as
`parent_lsn`.

**Compute spec** (`GET /compute/api/v2/computes/:id/spec`, called by
compute_ctl). The bearer token is `NEON_CONTROL_PLANE_TOKEN`, an Ed25519 JWT
with `scope: "tenantendpoint"`, the project's `tenant_id`, and `compute_id` set
to the endpoint id (Neon's `Claims.endpoint_id` is a UUID, so the endpoint id
travels in `compute_id`). The route accepts only a token signed by our key whose
`compute_id` equals the URL and whose tenant owns that endpoint: a compromised
compute cannot read another endpoint's spec, which carries a tenant-scoped
storage token. `401` for a bad token, `403` for another endpoint or tenant,
`404` for an unknown endpoint, and `503` (which compute_ctl retries) while
placement is missing or the controller is unreachable. Returns
`{status: "attached", spec, compute_ctl_config: {jwks}}`:

- `format_version: 1.0`, `suspend_timeout_seconds`, `cluster.roles` (name +
  SCRAM secret), `cluster.databases`, `cluster.settings` with the base GUCs
  (`wal_level=logical`, `synchronous_standby_names=walproposer`,
  `shared_preload_libraries=neon,pg_cron,pg_stat_statements`,
  `password_encryption=scram-sha-256`, `listen_addresses=*`, `port=5432`,
  `max_replication_write_lag=500MB`, `max_replication_flush_lag=10GB`,
  `fsync=off`, `restart_after_crash=off`, and `max_connections`,
  `shared_buffers`, `effective_cache_size`, `maintenance_work_mem` scaled from
  the compute size). The `neon.*` GUCs are not repeated: compute_ctl writes
  them from the spec fields (`compute_tools/src/config.rs`).
- `tenant_id`, `timeline_id`, `project_id`, `branch_id`, `endpoint_id`,
  `mode` (`Primary` for `read_write`; `Replica` for `read_only`, which gets
  `primary_conninfo` through the safekeepers instead of walproposer).
- `pageserver_connection_info` built from the controller's
  `GET /debug/v1/tenant/:id/locate` response (admin scope), mirroring
  `tenant_locate_response_to_conn_info` in Neon's `control_plane/src/endpoint.rs`.
  Shards are keyed by `ShardIndex`, `<2 hex shard><2 hex count>`: `0000` for an
  unsharded tenant.
- `safekeeper_connstrings` (`<host>:5454`) and `safekeepers_generation` from the
  branch row.
- `storage_auth_token`: a `tenant`-scoped JWT for that tenant.
- `delta_operations`: `delete_db` entries only while a database is being
  dropped.

**Wake** (`GET /proxy/wake_compute?endpointish=`). Strip a `-pooler` suffix
to find the endpoint. If no pod is running, claim the endpoint (`idle ->
starting`, a compare-and-set on the endpoint row, so replicas of neon-glue and
the worker never both start it), create `compute-<id>`, then poll compute_ctl
`GET :3080/status` (JWT with `aud: ["compute"]`, `scope: "compute_ctl:admin"`)
until `running`. Return `{address: "<podIP>:5432"}` (or `:6432` for `-pooler`)
with `aux: {endpoint_id, project_id, branch_id, compute_id, cold_start_info}`;
`cold_start_info` is `pool_miss` for a start and `warm` otherwise (the proxy
accepts no other values from a control plane). Concurrent wakes for one
endpoint share a single in-flight start. A `starting` claim older than six
minutes is presumed abandoned and taken over; a failed start deletes the pod
and returns the endpoint to `idle`. Unknown or deleted endpoints answer `404`
with reason `ENDPOINT_NOT_FOUND`; a start that fails answers `503` with
`retry_info.retry_delay_ms`, which is how the proxy decides to retry. The error
body is the proxy's own (`{error, status: {code, message, details: {error_info,
retry_info}}}`).

**Access control** (`GET /proxy/get_endpoint_access_control?endpointish=&role=`)
returns `{role_secret, project_id, account_id}` (`role_secret` is empty when
the role does not exist) and `allowed_ips` when the project restricts them.
`GET /proxy/endpoints/:id/jwks` returns `{jwks: []}`: JWT login to Postgres is
not offered. Every `/proxy/*` route requires `NEON_PROXY_TO_CONTROLPLANE_TOKEN`,
compared in constant time.

**Suspend.** The worker polls every running compute's `/status` each
`ALLOYDB_IDLE_SWEEP_SECONDS`. The idle clock is the later of compute_ctl's
`last_active` and the endpoint's `last_active_at` (stamped when the control
plane wakes it), so a connection the proxy just opened is not undone by a stale
value. When it is older than the endpoint's `suspend_timeout_seconds` (default
300, `0` = never), the worker claims `running -> suspending`, calls `POST
/terminate?mode=fast` (failure is logged, not fatal) and deletes the pod. A
compute that reports `failed` or `terminated`, or that stays unreachable for
three sweeps in a row, is cleaned up the same way.

**Storage-controller hooks.** `PUT /storcon/notify-attach` and
`PUT /storcon/notify-safekeepers` require `CONTROL_PLANE_JWT_TOKEN` as the
bearer. They are the endpoints named in `storage_controller/src/compute_hook.rs`
and the statuses are the ones the controller acts on:

| Status | Meaning |
| --- | --- |
| `200` | applied, or nothing was running |
| `423` | stored, but a compute is still starting and may have the old placement; the controller retries the reconcile later |
| `503` | a running compute could not be reloaded (or the controller's node list was unavailable); retried |
| `404` | unknown tenant or timeline; the controller tolerates it while a tenant is being created |
| `400`, `401` | bad body or token; never retried |

`notify-attach` does not store the pageserver placement: spec building asks
the controller (locate) each time, so the hook only reloads running computes,
pushing a spec built from the notification and the controller's node list.
`notify-safekeepers` stores the placement on the branch row (a notification
with an older generation than the stored one is ignored; hostnames, which the
controller marks informational, fall back to `safekeeper-<id - 1>.safekeeper.neon.svc.cluster.local`)
and then reloads running computes. A reload is `POST /configure` on
compute_ctl with the new spec, which waits until the compute is `running` again.

**Registration.** Every `ALLOYDB_REGISTRATION_SECONDS` the worker upserts
safekeepers `1..ALLOYDB_SAFEKEEPER_COUNT` (`POST /control/v1/safekeeper/:id`:
host `safekeeper-<id - 1>.safekeeper.neon.svc.cluster.local`, ports 5454 and
7676, zone `az-<id>`) when they are missing or differ, moves any that are
`Activating` to `Active` (`POST .../scheduling_policy`), and copies the
pageservers from `GET /control/v1/node` into the `node` table. Safekeepers an
operator paused or decommissioned keep that policy.

## Data API

PostgREST (`v16.4`) runs as one sidecar container per Data API database inside
the endpoint's compute pod. Enabling and disabling go through the operations
above; serving goes through the gateway.

Settings were checked in the PostgREST tree at tag `v16.4`:
`docs/references/configuration.rst` (`db-uri` 612, `db-pool` 436,
`db-channel-enabled` 319, `jwt-secret` 696, `jwt-role-claim-key` 675,
`server-host` 893, `admin-server-host` 149), `docs/references/auth.rst`
(asymmetric keys and JWKS, 114-170), `docs/references/schema_cache.rst`
(reloading, 51-170), `docs/references/admin_server.rst` and
`src/library/PostgREST/Cors.hs`. `GHCRTS` is honoured because the binary is
linked with `-rtsopts` (`postgrest.cabal:201`).

### Roles and why they come from SQL

compute_ctl creates every role in the spec with `CREATEROLE CREATEDB BYPASSRLS
REPLICATION IN ROLE neon_superuser` (`compute_tools/src/spec_apply.rs`, the
`CREATE ROLE` at the end of phase `CreateAndAlterRoles`), and a spec role
cannot be `NOLOGIN` or `NOBYPASSRLS`. A spec role would therefore ignore
row-level security, which is the point of the `anonymous` and `authenticated`
roles. So the control plane creates the three Data API roles with SQL after the
compute reports `running`, connecting to the pod IP on 5432 as the database's
**owner role** (it has `CREATEROLE` from the spec). Roles that are not in the
spec are left alone by later spec applies, and the Neon proxy only admits roles
whose SCRAM secret `get_endpoint_access_control` returns, so none of the three
can log in from outside the pod.

`data_api.enable.bootstrap` runs these statements (`data-api/bootstrap.ts`),
each idempotent:

- `authenticator`: `LOGIN NOINHERIT`, password given as a SCRAM secret so the
  plaintext never appears in a statement the server could log. If the role
  exists the password is set again where the owner may, which repairs drift.
- `anonymous` and `authenticated`: `NOLOGIN`, no other attribute, created only
  when missing. `GRANT anonymous, authenticated TO authenticator`, only when
  `pg_has_role(...,'MEMBER')` says it is missing: the roles are cluster-wide, so
  a second database with another owner may lack `ADMIN` on them.
- `GRANT USAGE ON SCHEMA public` to both. `GRANT ALL` on the tables, sequences
  and routines that exist in `public`, and `ALTER DEFAULT PRIVILEGES IN SCHEMA
  public GRANT ALL` for the ones the owner creates later, to `authenticated`
  only. `anonymous` gets no table privileges: an unauthenticated request sees
  nothing until the project grants it `SELECT` on what it wants public.
  `GRANT ALL ON ALL ...` only warns for objects the owner cannot grant on, and
  default privileges apply to objects created by the role that ran the
  statement, so tables created by other roles need their own `GRANT`.
- The owner must have a sealed password (`role.password_enc`). The enable route
  answers `409` otherwise and says to reset the role's password first; a login
  rejected with `28P01` fails the operation for good with the same advice.

### Schema cache reload

PostgREST caches the schema. Its documented reload is `NOTIFY pgrst, 'reload
schema'`, fired automatically by an event trigger
(`docs/references/schema_cache.rst`, "Automatic Schema Cache Reloading"). The
bootstrap installs the documented functions (in a schema `alloydb_data_api`, so
they are not exposed as API routes) and tries to create the two event triggers
`pgrst_ddl_watch` and `pgrst_drop_watch`. Stock PostgreSQL only lets a
superuser create an event trigger, and the owner role is not one. The step
treats SQLSTATE `42501` on that statement as a known limit, records
`schemaReload: "manual"` in its output, and carries on. **Limitation:** where
the triggers cannot be created, DDL does not refresh the API by itself; run
`NOTIFY pgrst, 'reload schema'` (any role can) after changing the schema. The
bootstrap sends one itself at the end. Whether Neon's Postgres build lets
`neon_superuser` create event triggers is not verified; the step works either
way.

### Sidecars

The compute runtime's `sidecars` hook (`data-api/sidecars.ts`) builds the
containers on every cold start from the current database state: one per
database with `data_api_enabled`, named `postgrest-<db>`, with

| Setting | Value |
| --- | --- |
| `PGRST_DB_URI` | `postgres://authenticator:<password>@127.0.0.1:5432/<db>`: direct to Postgres, not PgBouncer, because PostgREST needs `LISTEN` for `NOTIFY pgrst` |
| `PGRST_DB_SCHEMAS`, `PGRST_DB_ANON_ROLE` | `public`, `anonymous` |
| `PGRST_JWT_SECRET` | the project's JWKS as JSON (custom keys if set, else the platform key) |
| `PGRST_JWT_ROLE_CLAIM_KEY` | `$.role` |
| `PGRST_SERVER_HOST`, `PGRST_SERVER_PORT` | `!4` (any IPv4, so the gateway can reach the pod IP), `3000 + data_api_index` |
| `PGRST_ADMIN_SERVER_HOST`, `PGRST_ADMIN_SERVER_PORT` | `127.0.0.1`, `3100 + data_api_index` |
| `PGRST_DB_POOL`, `GHCRTS` | `5`, `-N1` (one Haskell capability) |

The index is stored on the database row, assigned once as the branch's highest
index plus one and never reused, and limited to 0-49 so that the API ports stop
below compute_ctl's 3080. If a request could reach a sidecar through a stale
position (the pod is rebuilt only on restart), it would answer for another
database; a fixed position per database rules that out. PostgREST reads its
environment once, so enabling, disabling or changing the JWKS restarts the
compute: `suspend`, then `wake`. Connections of that compute drop; an idle
compute simply builds the new pod at its next start. Read-only endpoints get the
sidecar at their next start; only the `read_write` endpoint is restarted and
bootstrapped.

`infra/k8s/control-plane/compute-networkpolicy.yaml` limits the PostgREST ports
of compute pods: TCP 3000-3049 is open to the gateway pods only and 3100-3149 to
nobody, while every other port stays open as before. Credentials are in the pod
environment (`PGRST_DB_URI`), readable by anyone who can read pods in
`neon-compute`, which only the control plane's service account can.

### JWKS and test tokens

`neon_project.data_api_jwks` holds the platform-issued public key, created with
its sealed private key the first time a database enables the Data API. It is an
ES256 key, not EdDSA: PostgREST decodes tokens with `jose-jwt`, and ES256 is the
asymmetric algorithm certain to be supported by every build, while Ed25519
depends on the library version. `POST /v1/projects/:id/data_api/token` signs
`{role, sub?, iss, iat, exp}` with it (`role` is `anonymous` or `authenticated`,
up to 24 hours), so the console can offer a working token without an identity
provider. `PUT /v1/projects/:id/data_api/jwks` sets the project's own public
keys (private and shared-secret members are rejected) or `null` to go back; it
queues a project-wide restart and, while custom keys are set, the test-token
route answers `409` because those tokens would not verify.

### Gateway

`https://ep-<id>.apirest.alloydb.net/<db>/rest/v1/<path>` (mode
`data-api-gateway`, any host label under `apirest.alloydb.net` reaches it
through Traefik). For each request it:

1. parses the host (`ep-<id>`) and path (`/<db>/rest/v1...`); anything else is
   `404` with a PostgREST-shaped body `{code, message, details, hint}`;
2. answers a CORS preflight itself without waking anything, with the headers
   PostgREST sends (origin echoed, `Allow-Credentials`, the methods, the
   requested headers plus `Authorization`, `Max-Age: 86400`); the gateway's own
   errors carry the same CORS headers, proxied responses keep PostgREST's;
3. checks the endpoint and that the database has the Data API on (`404`
   `data_api_not_enabled` otherwise);
4. wakes the compute through the shared runtime (store, storage controller and
   Kubernetes access, like neon-glue); a start that fails is `503` with
   `Retry-After: 2`;
5. waits up to 15 s for the sidecar port to accept TCP, then streams the request
   to `http://<podIP>:<3000 + index>/<path>?<query>` with the body unbuffered
   (`duplex: half`), `Authorization` untouched, hop-by-hop headers removed and
   `Accept-Encoding: identity`, and streams the answer back. Connection
   failures are `502`, no answer within two minutes is `504`.

Token verification, roles and row-level security are PostgREST's and
Postgres's. A request without a token runs as `anonymous`.

## libSQL flows

Verified against `libsql-server-v0.24.33`; file references are in that tree.

**Naming.** A database is the namespace `<name>-<team>` (`libsql/names.ts`).
`team` is the console organization id when that is already a lowercase label of
at most 20 characters, else `t` plus ten hex characters of its SHA-256, so two
organizations never share a team. sqld itself only requires a non-empty name
(`namespace/name.rs:47-53`), but the name is also the directory name and the
first label of the Host header (`http/user/db_factory.rs:115-120`), so the
control plane enforces one DNS label of 1-63 characters (the contract allows
database names up to 42). Names are unique per organization; the public host is
`<namespace>.lite.alloydb.net`.

**Placement.** The node with `libsql` in `node.roles`, `capacity.ready` not
false and the largest free share, `(capacity - databases) / capacity` with
`capacity.libsqlMaxDatabases` defaulting to 200 (`--max-active-namespaces 200`).
Ties go to the lowest id; no node with room is `503 no_capacity`. A fork stays
on its source's node because sqld forks inside one server.

**Node sync.** Every `ALLOYDB_REGISTRATION_SECONDS` the worker lists Kubernetes
Nodes and upserts `node` rows: id from `alloydb.net/node-id`, address from the
annotation `alloydb.net/tailscale-ip` or else `InternalIP` (k3s `node-ip` is the
Tailscale address), zone from `topology.kubernetes.io/zone`, roles from the
`alloydb.net/{pageserver,libsql,compute}=true` labels (replacing the stored
roles), and `capacity.ready` from the Ready condition. Nodes without the id
label and duplicate ids are skipped.

**Admin API** (`http://<tailscale ip>:8081`, `libsql/admin-client.ts`;
`http/admin/mod.rs`):

| Call | Detail |
| --- | --- |
| auth | `Authorization: Basic <key>`. The key is compared as is, not base64-decoded, and split on whitespace (`mod.rs:209-235`) |
| create | `POST /v1/namespaces/<ns>/create`, JSON object body; `max_db_size` is a number of bytes (`CreateNamespaceReq`, 367-386, `bytesize` serde). "Already exists" is `400` with `{"error": "Namespace ... already exists"}` (`error.rs:193`), which counts as success |
| fork | `POST /v1/namespaces/<from>/fork/<to>`, optional `{"timestamp"}` in chrono `NaiveDateTime` form, UTC without a zone (`2026-01-02T03:04:05`; 444-471). Sent without a body for "now" |
| delete | `DELETE /v1/namespaces/<ns>` with `{"keep_backup": bool}`; no body or `false` also prunes the bottomless backup (512-533). A missing namespace is `404`, which counts as success |

sqld refusing a request with a 4xx other than 429 fails the operation at once;
network errors and 5xx retry.

**Kubernetes.** For node `N`, a selector-less Service `sqld-node-N` in `libsql`
(port 8080) and a hand-managed EndpointSlice with the same name, labelled
`kubernetes.io/service-name` and `endpointslice.kubernetes.io/managed-by:
alloydb-control-plane`, pointing at the node's Tailscale IP; the slice is
corrected if the address changes, the Service is created once. Per database, a
Traefik `IngressRoute` named like the namespace: entry point `websecure`, rule
``Host(`<ns>.lite.alloydb.net`)``, service `sqld-node-N:8080`, TLS secret
`lite-wildcard-tls` (issued into `libsql` by cert-manager). Existing objects are
compared and replaced only when they differ.

**Tokens** (`libsql/tokens.ts`) are EdDSA JWTs signed with the
`libsql-jwt-signing` key, whose public half every node loads with
`--auth-jwt-key-file` (`parse_jwt_keys` accepts a PEM, `auth/parsers.rs:25-44`).
Claims `{iat, exp?, p: {rw: {ns: [<ns>]}}}` for read-write or `ro` for
read-only: `Token` has `id`, `a`, `p`, `exp` (`auth/user_auth_strategies/jwt.rs:56-66`),
`p` is `Authorized` with `ro`, `rw`, `roa`, `rwa`, `ddl` (`auth/authorized.rs:10-23`)
and each is a `Scopes` whose `ns` lists namespaces (178-184). `exp` is in
seconds and checked when present; a token without it never expires.

**Delete** closes the route first, then removes the namespace, so no connection
reaches a database that is going away. The row is soft-deleted in the request.

## Public API (mode `api`)

All routes require `Authorization: Bearer <ALLOYDB_API_TOKEN>` (held by the
console's server code) plus `X-AlloyDB-Org` and `X-AlloyDB-Project` headers
that the console sets after its own membership checks. Request and response
bodies are the zod schemas in `@repo/control-plane-contract`; errors are
`{error: {code, message}}`. Shapes follow Neon's v2 API where one exists.

Scoping is enforced in every query, not only at the route: a project, branch,
endpoint, role or database is found only when its project belongs to both the
given organization and console project, and an id from anywhere else is the
same `404` as an id that does not exist. Operations are scoped the same way
(`operation.console_org_id`). Tests cover this for another console project,
another organization, and the same console project under another organization,
in memory and against PostgreSQL.

| Route | Result |
| --- | --- |
| `POST /v1/projects` | `202`, the project, default branch, endpoint, owner role with its generated password (shown once) and a connection URI; `409` if the console project already has one |
| `GET /v1/projects`, `GET /v1/projects/:id` | the console project's project |
| `DELETE /v1/projects/:id` | `202`, `project.delete` |
| `GET`, `POST /v1/projects/:id/branches`, `GET`, `DELETE .../branches/:branch` | `POST` forks `parent_id` (default branch) at `parent_lsn`; `409` for a duplicate name, the default branch, or a branch with children |
| `GET`, `POST /v1/projects/:id/endpoints`, `GET`, `PATCH`, `DELETE .../endpoints/:endpoint` | one `read_write` endpoint per branch (`409` otherwise); a size change restarts a running compute |
| `POST .../endpoints/:endpoint/start`, `/suspend` | `202`, `endpoint.start`, `endpoint.suspend` |
| `GET`, `POST .../branches/:branch/roles`, `POST .../roles/:role/reset_password` | the password is returned once; only the SCRAM secret is stored |
| `GET`, `POST .../branches/:branch/databases`, `DELETE .../databases/:db` | `:db` is the database name |
| `PUT`, `DELETE .../branches/:branch/databases/:db/data_api` | `202`; turns the Data API on (`409` without a `read_write` endpoint, a stored owner password or a free sidecar slot) or off |
| `GET`, `PUT /v1/projects/:id/data_api/jwks` | the effective keys and their `source` (`platform` or `custom`); `PUT` takes `{jwks}` or `{jwks: null}` and answers `202` with the restart operation |
| `POST /v1/projects/:id/data_api/token` | `{role?, sub?, expires_in_seconds?}`: a test token signed with the platform key |
| `GET`, `POST /v1/libsql/databases` | list the console project's databases; create one (`503` with no capacity, `409` for a taken name) |
| `GET`, `DELETE /v1/libsql/databases/:id` | `DELETE` takes `?keep_backup=true` |
| `POST /v1/libsql/databases/:id/fork` | `{name, timestamp?}`; the source must be `active` |
| `POST /v1/libsql/databases/:id/tokens` | `{access?, expires_in_seconds?}`: a token for the namespace (`200`); the database must be `active` |
| `GET /v1/operations/:id` | the operation |

Mutations answer `202` with the changed resource and an `operation`; `423`
means the project has an operation in flight; `400` names every invalid field.

libSQL databases are scoped like Neon resources: by organization and console
project, in every query. They share the console project's one-active-operation
lock with the Neon resources.
