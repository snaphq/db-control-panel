# Multi-site architecture

Every tenant site is a separate Next.js app under `sites/*`, built and
deployed on its own, but almost all of its behavior is shared. The design
goal is that a site is thin: its identity, brand, and a few pages. A fork of
the whole app per site drifts; a shared route tree does not.

## What a site owns

| File | Purpose |
| --- | --- |
| `src/site.config.ts` | Identity: tenant id/slug, name, description, production domain, public pages, agent markdown, MCP server name and toolsets. Imported by `next.config.ts`, so it may only have type imports. |
| `src/app/layout.tsx` | Renders `SiteRootLayout` from `@repo/site-kit/root-layout` and imports the site's `globals.css`. |
| `src/app/globals.css` | Imports `packages/react-ui/src/styles/theme.css` and overrides design tokens for the brand. |
| `src/app/page.tsx`, legal/marketing pages | Site-specific public pages listed in `publicPaths`. |
| `src/components/Container/PageWrapper.tsx` | Public-page chrome (header/footer) used by shared routes. |
| `src/lib/source.ts`, `source.config.ts`, `content/blog` | The site's fumadocs collections (docs mirror of `docs-public/` and its own blog). |
| `src/proxy.ts` | Re-exports the shared proxy; `config.matcher` must stay literal here. |
| `next.config.ts` | Pins `SITE_TENANT_ID` from `site.config.ts` (see below). |
| `.env.development` | Committed, non-secret local URL (`NEXT_PUBLIC_APP_URL`, also the auth base URL). |

Everything else under `src/app` is generated.

## Shared routes and generated shims

`packages/site-kit/src/app` holds the route tree every site serves: auth
pages, account and dashboard, API routes, `/mcp`, OAuth/OIDC, `.well-known`,
`/auth.md`, docs, blog, sitemap, and robots. Next.js only discovers routes
that exist inside an app, so `scripts/sync-site-routes.ts` writes one-line
shims into each site:

```ts
// @generated by scripts/sync-site-routes.ts from @repo/site-kit — do not edit.
export { GET } from "@repo/site-kit/app/r/[code]/route";

export const runtime = "nodejs";
export const dynamic = "force-dynamic";
```

Segment config (`dynamic`, `revalidate`, `runtime`, `maxDuration`, …) is
copied as a literal because Next.js reads it statically from the route file.
Run `bun run sites:sync` after adding, removing, or changing the exports of a
shared route; the pre-commit hook runs `bun run check:site-routes` and fails
on missing, stale, or orphaned shims.

A site overrides a shared route by committing its own file at the same path
without the generated marker; the generator then leaves it alone.

## The `@site/*` contract

Shared code that needs site-owned modules imports them through the `@site/*`
alias, which each site maps to its own `src/*` in `tsconfig.json`:

- `@site/site.config` — the site's `siteConfig`
- `@site/lib/source` — `docsSource` and `blog`
- `@site/components/Container/PageWrapper` — public-page chrome

Keep this contract small. `packages/site-kit/tsconfig.json` and its Vitest
config map `@site/*` to `sites/net.alloydb.console/src` as the reference site for
type-checking and tests; knip and fallow treat the contract modules as entry
points.

## Tenancy per site

Each site serves exactly one tenant. In production the tenant comes from the
request Host header (`resolveTenantFromHost`, via `tenant_domain`). Locally
every site runs on `localhost`, so `next.config.ts` pins
`env.SITE_TENANT_ID` from `site.config.ts`, and `getLocalTenantId()` in
`@repo/database` uses it for local hosts (development only; production never
maps local hosts to a tenant).

`bun run db:seed:sites` reads every `sites/*/src/site.config.ts` and creates
or updates its `tenant` and primary `tenant_domain` rows. Two sites may not
claim the same tenant.

Browsers share cookies across ports, so signing in to two sites on
`localhost` at once shares one cookie jar; use different host names (for
example `console.localhost:8801`) when testing both at the same time.

## MCP per site

`/mcp` on each site registers the toolsets listed in
`siteConfig.mcp.toolsets` (see `SITE_MCP_TOOLSETS` in
`packages/mcp-server/src/site-tools.ts`) under the site's own
`siteConfig.mcp.serverName`. `mcp.readOnly: true` registers only tools
annotated `readOnlyHint: true`, for demo or sandbox sites. Admin tools are
never registered on a site; they live on the backend
([Backend admin portal](/architecture/backend-admin)).

## Adding a site

There are two kinds of site, discriminated by `stack` in `site.config.ts` and by
whether the site depends on `@repo/site-kit`.

### A site on the shared route tree (the usual case)

1. Copy `sites/net.alloydb.console` to `sites/<folder>` and set the package name and
   dev port (`package.json`), local URLs (`.env.development`), and
   `src/site.config.ts`.
2. Brand it in `src/app/globals.css` and the site-owned pages.
3. `bun install && bun run sites:sync`, then `bun run db:seed:sites`.
4. Add a `dev:<name>` root script and a matrix entry in
   `.github/workflows/deploy-vercel.yml` and `deploy-vercel-preview.yml`, and
   create its Vercel project with the site folder as Root Directory.

### A standalone site on its own framework

A site on another framework (for example SolidStart or Astro) consumes none of
the shared route tree. The only structural requirement is that the site must
**not** list `@repo/site-kit` in its `dependencies` — that absence is what
makes `scripts/sync-site-routes.ts` skip it, so no shims are generated and no
flag is needed. Type-only imports from `@repo/site-kit` (for example
`SiteConfig`) resolve through a tsconfig path mapping instead, which does not
create the dependency.

Such a site exports a `StandaloneSiteConfig` with `stack: "standalone"` and
omits `markdown` and `mcp`, because it serves neither. It still gets its
tenant rows from `bun run db:seed:sites`, which reads only the
`SiteConfigBase` fields.

Everything else — the deploy matrix row, the Vercel project, the `dev:<name>`
script — is the same. Note that a framework with its own Node requirement
needs its own `node_version` in the deploy matrix. A framework that fixes its
middleware filename (such as Astro's `src/middleware.ts`) also needs the
matching exemption in `scripts/check-no-middleware.ts`.
