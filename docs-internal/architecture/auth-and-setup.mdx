# Authentication and setup architecture

## Provider boundary

`@repo/auth` exposes the selected provider through a stable package surface:
client helpers, server/session helpers, configuration, and shared types. The
initial repository includes provider templates under
`.setup/templates/auth/{better-auth,next-auth,authkit,clerk}/`; setup copies the
selected template and removes unused provider implementation files.

The app owns route composition under `apps/next-app/src/app/api/auth` and UI
flows under `apps/next-app/src/app/auth`. Shared package consumers should use
`@repo/auth` exports instead of importing a provider template directly.

## Setup lifecycle

`.setup/setup.ts` is the unified entry point. It can initialize the auth
provider, merge environment values, run optional setup scripts, and guard the
development command until initialization is complete. Auth initialization
backs up files before rewriting them and records an end-user lock artifact;
those artifacts are never committed.

Treat provider switching as a destructive workflow: commit feature work first,
run the documented `--force` path, inspect the diff, and restore the generated
state before continuing. The detailed reset procedure lives in `CLAUDE.md`.

## Security invariants

- Secrets stay in `.env.local` or the deployment secret store.
- Provider choice and generated files must agree; do not mix provider APIs.
- Session and organization checks happen at the server boundary before a
  protected mutation.
- Better Auth is backed by a tenant-bound adapter. Core auth, organization,
  OIDC, passkey, and two-factor reads and writes require the request tenant;
  OIDC access-token and consent rows also require the exact protected-resource
  context. Transactions wrap their adapter so plugin-direct writes cannot
  bypass these predicates.
- Passkey relying-party configuration must match the deployed domain.
- Auth errors should carry enough context for diagnosis without exposing
  credentials or sensitive user data.
