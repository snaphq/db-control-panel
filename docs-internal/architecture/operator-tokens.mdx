# Operator tokens

Operator tokens replaced the retired personal account token model (`cet_…`). Programmatic requests (today `/mcp`; future public APIs) authenticate
as a named **operator** owned by a user, so requests are attributed to the
specific machine identity instead of an anonymous account credential. The web
application continues to use Better Auth sessions exclusively.

## Data model

- `operator` — owner (`user_id`), `tenant_id`, `name`, optional `description`,
  `status` (`active` / `suspended`), JSON `scope`, and terminal `revoked_at`.
- `operator_token` — credential rows for an operator: `label`, `token_hash`
  (unique, SHA-256 hex), display `token_prefix`, `expires_at`, `last_used_at`,
  `revoked_at`. One operator may hold multiple independently revocable tokens.
- `operator_activity` — per-event activity log for operator-attributed MCP
  events, written for every event (see below) and shown on the operator
  dashboard, filterable by `credential_id`.

Scope JSON:

```json
{ "mode": "all_owned" }
{ "mode": "organizations", "organizationIds": ["org_..."] }
```

`parseOperatorScope` rejects malformed values and fails closed; corrupt stored
scope makes verification return `null` (401), never a 500.

## Verification and authorization

`verifyOperatorToken(req)` (server-only):

1. Requires a single `Bearer` credential with the `opt_` prefix.
2. Looks up the token hash with `operator_token.revoked_at IS NULL`, joined to
   its operator, and rejects expired tokens, `status !== "active"`, or a
   revoked operator.
3. Resolves the request host tenant and requires the token tenant, operator
   tenant, and owner user tenant to match; archived owners are rejected.
4. Resolves reachable organizations live with one `member JOIN organization`
   query: `all_owned` keeps only current `owner` roles; explicit scope keeps
   current memberships in the listed IDs. Zero reachable organizations is not
   an authentication failure — org-requiring operations fail later.
5. Derives protocol scopes: always `api.read`; `api.write` only when at least
   one reachable organization grants `owner`/`admin`.
6. Updates `lastUsedAt` best-effort; failures are swallowed.

All failure modes return the same generic 401 `invalid_token` at the MCP
boundary, so callers cannot distinguish unknown, expired, revoked, suspended,
or cross-tenant credentials.

Tools and future routes resolve the acting organization with
`requireOperatorOrganization({ organization, write })`, which reads the live
operator context from the MCP request store (no extra queries) and enforces:

- an operator credential (`actorType === "operator"`), otherwise 403;
- a reachable organization, otherwise 403 with guidance;
- unambiguous selection: explicit slug/ID, auto-select when exactly one
  organization is reachable, otherwise 400 listing accessible slugs;
- unknown/not-reachable organization → 404 (no cross-tenant enumeration);
- `write: true` requires the live role `owner` or `admin`.

Global `site-admin`/`admin` user roles do not bypass operator scope.

## Attribution and activity sinks

Every MCP request, response, and tool call carries the actor fields from the
request context: `actorId = operator.id`, `actorType = "operator"`,
`actorName`, `credentialId`, `authMethod = "operator_credential"`, and the owner
`userId`.

- **Database sink (always):** `packages/core/src/operators/activity.ts`
  registers an `McpActivitySink` via `registerMcpActivitySink` from
  `@repo/mcp-chatgpt`. The logger invokes it synchronously, exactly once, for
  every operator-attributed entry (non-operator entries never reach it), and it
  inserts an `operator_activity` row fire-and-forget. It is idempotently
  registered and loaded by `packages/site-kit/src/app/mcp/route.ts`.
- **Axiom (additional, optional):** when `AXIOM_TOKEN` is set, operator events
  are also routed to `AXIOM_OPERATOR_DATASET` (or `AXIOM_DATASET` when unset or
  empty) and tagged with `project.type: "operator"` so they can be filtered
  separately. Ingest failures are swallowed and do not re-trigger the database
  sink, so activity is never double-written.

Both sinks are best-effort: logging never throws, never blocks a request, and
never changes a response; a throwing sink does not prevent the Axiom send.
Non-operator events only go to Axiom and are a no-op when Axiom is off.

## Operator detail API

Session-only routes backing `/account/settings/operators/[id]`:

- `GET /api/account/operators/[id]` → `{ operator }` with all tokens, including
  revoked keys (`revokedAt` set), ordered active first then revoked, newest
  first within each group; 404 `operator_not_found` for missing, foreign, or
  revoked operators.
- `GET /api/account/operators/[id]/activity?credentialId=&limit=` →
  `{ entries }` from `operator_activity`, newest first; `limit` defaults to 50
  and is clamped to 1..200.
- `PATCH /api/account/operators/[id]/tokens/[tokenId]` with
  `{ label: string | null }` → `{ token }`. Labels are trimmed; empty clears.
  Errors: 400 `invalid_label` / `label_too_long`, 404 `token_not_found`, 409
  `token_revoked` (revoked keys are immutable history).

Scopes remain on the operator; tokens carry no scope of their own.

## Security invariants

- Only SHA-256 hashes are stored; plaintext (`opt_…`) is returned exactly once
  at creation and never logged or persisted.
- Credentials are tenant-bound; host, token, operator, and owner tenants must
  all agree.
- Organization scope, membership, and roles are re-resolved on every request;
  scope JSON is not an authorization cache.
- Management routes (`/api/account/operators/**`) are session-only. Operator
  credentials cannot create, edit, or revoke operators.
- Revocation is soft (`revoked_at`) so historical attribution stays resolvable;
  list endpoints exclude revoked rows, while the operator detail endpoint
  returns revoked tokens as read-only history.

## Cutover and operations

- The three tables are part of the Drizzle schema and are created by
  `bun run db:push` (see [Database migrations](/operations/migrations)).
- `/mcp` detects `cet_` credentials and returns an actionable 401 pointing at
  `/account/settings/operators`; agent-JWT and OAuth verifiers skip `opt_`
  values to avoid misparsing.
- `operator_activity` is append-only and written for every operator event;
  define pruning by age in every environment.
