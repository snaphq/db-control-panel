# com.site-c

`sites/com.site-c` is the third tenant site and the first one that does **not**
consume the shared `@repo/site-kit` route tree. It runs SolidStart 2 on Vite 8
with Hono for `/api` and Better Auth for identity, while sharing the
monorepo's single `DATABASE_URL` and owning its own tenant.

| | com.site-a / com.site-b | com.site-c |
| --- | --- | --- |
| Framework | Next.js 16 App Router | SolidStart 2 + Vite 8 |
| Shared routes | `@repo/site-kit` | none, owns `src/routes` |
| API | Next route handlers | Hono, mounted at `/api` |
| Styling | Tailwind 4 + `@repo/react-ui` | Tailwind 4 + its own Solid primitives |
| Node | 22 | **24+** (SolidStart 2 requirement) |
| Deploy output | `.next` | Nitro (`.output` locally, Vercel on Vercel) |

## Why it does not use site-kit

`packages/site-kit/src/app` is a Next.js App Router route tree. Its route files
depend on `next/headers`, `next/server`, and React components from `@repo/react-ui`.
SolidStart discovers routes under `src/routes` and renders Solid, so none of it
can be re-exported into this app. The reuse audit found the rest of the monorepo
is framework-neutral (11 of 13 packages, ~200 of ~436 files), so only `ui` and
`site-kit` are genuinely unavailable.

Opting out is a single decision: **do not list `@repo/site-kit` in the site's
`dependencies`**. `scripts/sync-site-routes.ts` selects the sites it generates
Next.js shims for by exactly that dependency, so its absence is a complete
opt-out with no flag and no script change. The `SiteConfig` type import in
`src/site.config.ts` is type-only and resolves through a tsconfig path mapping
instead, so it does not reintroduce the dependency.

`site.config.ts` exports a `StandaloneSiteConfig` (`stack: "standalone"`), which
carries the tenant identity but no `markdown` or `mcp` — this site serves
neither agent markdown nor an MCP endpoint. See
[Multi-site architecture](/architecture/multi-site) for the `AnySiteConfig`
union that `db:seed:sites` consumes.

## Tenant resolution

One guard, in `src/http/tenant-guard.ts`, runs on **every** request:

1. Resolve the tenant with `resolveTenantFromHost` from `@repo/database`.
2. If it does not resolve, return **404**. There is no default fallback. Every
   site shares one database, so a request that cannot be attributed to a tenant
   must not be served under some other identity. This mirrors
   `getCurrentTenant()` in `@repo/core`.
3. Only then route `/api/*` to Hono, passing the tenant as the fetch bindings so
   it arrives as `c.env.tenant`.

The dashboard API takes **no tenant parameter anywhere**. A client cannot ask for
another tenant's data, because the only tenant a request can read is the one the
Host header resolved to. The read models in `src/server/queries.ts` accept an
already-resolved `tenantId` and only narrow from it.

`organization.tenantId` is the only tenant link on the billing and audit tables.
`org_audit_logs` has no `tenant_id` column of its own, so the Logs query joins
through `organizationId` — that join is not optional.

Locally, `next.config.ts` has no SolidStart equivalent, so `.env.development`
pins `SITE_TENANT_ID=site-c`, which `getLocalTenantId()` reads for local hosts.
In production `resolveTenantFromHost` never maps a local host to a tenant.
Because browsers share cookies across localhost ports, `multi-site.mdx` applies
here too: test alongside the other sites via `com-site-c.localhost:8803`.

## Auth

`/api/auth/*` is mounted in the Hono app against
`getBetterAuthServer({ cookieDelivery: "response" })`.

`cookieDelivery` exists because Better Auth's `nextCookies` plugin only exists to
re-apply `Set-Cookie` through Next's `cookies()` API. SolidStart returns the
Response as-is, so the plugin is unnecessary rather than merely unused. The
default stays `"next"`, which leaves every existing site byte-identical.
`getApiHandler()` also imports `better-auth/next-js` lazily, so this site never
pulls `next/headers` into its module graph.

One instance serves every tenant: each read and write is bound to the request's
tenant by `withTenantBoundAuthAdapter` inside `@repo/auth`.

## Vite and env

Two SolidStart differences bite here, both handled in `vite.config.ts`:

- **`server-only` breaks dev.** `@solidjs/start/middleware` imports React's
  `server-only` marker, whose default entry throws unless the `react-server`
  export condition is set. SolidStart never sets it, so every request 500s in
  `bun run dev` while `vite build` still succeeds. A `resolve.alias` points it at
  `src/shims/server-only.ts`, an empty module.
- **Vite does not populate `process.env`.** Next.js loads `.env` and `.env.local`
  automatically; Vite only exposes prefixed vars through `import.meta.env`. The
  config calls `loadEnv` with an empty prefix and copies into `process.env`
  without overwriting real environment variables, so `DATABASE_URL` (read
  straight from `process.env` by `@repo/database`) and the `SITE_TENANT_ID` pin
  both work.

`middleware` points at `tenant-guard.ts` rather than `middleware.ts`:
`check-no-middleware` rejects that filename at any depth, because Next.js 16
replaced it with `proxy`.

`tsconfig.json` maps `~/*` to `./src/*`, and the same prefix is aliased in
Vite, which does not read tsconfig paths. (`"@/*"` and a bare `"src/*"` are both
rejected by TypeScript 7, which removed `baseUrl`.)

## Deploy

Vercel only. `vite.config.ts` uses `nitro()` **after** `solidStart()`; Nitro
detects the platform during the build, so no preset argument is needed and
`vercel.json` deliberately sets **neither** `framework` nor `outputDirectory`.
The SolidStart preset's `.output` default belongs to SolidStart 1, and
`"framework": "nextjs"` copied from `sites/com.site-b/vercel.json` would break
the build. Vercel detects the SolidStart preset from `solid-js` and
`@solidjs/start` in the site manifest.

Locally Nitro resolves `node-server` and emits `.output/server/index.mjs`, which
is what `start` runs and what the parameterized Dockerfile expects.

**Node 24 is required.** The deploy workflows previously hardcoded
`node_version: '22'` for every matrix row. `node_version` is now a per-row
matrix field so the `site-c` row passes `24` while the other apps keep `22`.
`sites/com.site-c/package.json` also pins `engines.node: "24.x"`, which overrides
the Vercel project setting.

## Tests

`bun run test` in the site runs Vitest. Two suites, neither needing a database:

- `src/http/tenant-guard.test.ts` — cross-site isolation: unknown host 404s, a
  host is bound to its own tenant, one site's tenant never leaks to another, and
  a `?host=` query parameter cannot smuggle a tenant past the guard. Mocks
  `@repo/database` with a host-to-tenant map, following
  `packages/core/src/tenant-isolation.test.ts`.
- `src/server/queries.test.ts` — the read models bind the resolved tenant into
  their WHERE clause, join through `organization` for the audit log, page
  correctly, and report zero rather than throwing on an empty tenant.

CI runs site tests through `test.yml`, whose turbo filter was widened to include
`./sites/*` (it previously covered only `./packages/*` and `./apps/*`).
