# Database migrations

The database schema and Drizzle configuration live in `packages/database`.
Local development may use:

```bash
bun run db:push
```

For shared environments:

```bash
bun run db:generate
bun run db:migrate
```

## Review checklist

1. Confirm the schema change is owned by the correct schema module and remains
   tenant-safe.
2. Inspect generated SQL, indexes, constraints, and data backfill behavior.
3. Check the migration against a disposable non-empty database.
4. Apply it through the configured deployment process and verify a real query
   path, not only the migration journal.
5. Record rollback or forward-fix steps before production application.

Seeds and manual migration helpers are explicit scripts. They must not be
silently invoked by a normal app build or request.

The agent-readiness token-boundary changes are captured in the tracked
`packages/database/migrations-manual/agent_readiness_security.sql` forward
migration. Review it against the target database and apply it only through an
authorized migration run; local Drizzle output under `packages/database/drizzle`
is intentionally ignored.

Operator tokens are introduced by the tracked
`packages/database/migrations-manual/operator_tokens.sql` forward migration. It
creates `operator`, `operator_token`, and `operator_activity`, then renames
`account_api_token` to `account_api_token_archive` (hard cutover: retired
`cet_…` credentials stop authenticating). Apply it before deploying the release
that reads the new tables. Because the archive table is intentionally outside
the Drizzle schema, reserve `bun run db:push` for disposable databases and use
the manual migration or `db:migrate` for shared environments.
