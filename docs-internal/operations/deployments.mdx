# Deployment and runtime

Each web app is its own Vercel project: `apps/backend` and each deployed
`sites/*` app. These deployments run through GitHub Actions
(`.github/workflows/deploy-vercel.yml` on pushes to `main`,
`deploy-vercel-preview.yml` for pull requests), as a matrix with one entry per
app. An entry is skipped until its project id is configured.

The control plane is not a Vercel app. `.github/workflows/images.yml` builds
the control-plane and data-plane container images from pinned source revisions;
the Kubernetes resources under `infra/k8s/` define the workloads. Image builds
and cluster rollout are separate steps.

## Vercel

| App | Root Directory | Config |
| --- | --- | --- |
| `sites/net.alloydb.console` | repository root | root `vercel.json` (`--filter=net.alloydb.console`, output `sites/net.alloydb.console/.next`) |
| `apps/backend` | `apps/backend` | `apps/backend/vercel.json` |

The Vercel org id and every project id are hard-coded in the workflow matrix
(`project_id` per row, `vercel_org_id` on the deploy step), written at setup by
`set-vercel-projects.ts`; a row with an empty `project_id` is skipped.
`VERCEL_TOKEN` is the repository secret every deploy needs. The optional
`DATABASE_URL` secret turns on the `migrate` job (below). Each project needs its own runtime variables,
including its public URL (`NEXT_PUBLIC_APP_URL`) and each site's production domain (which must match
`site.config.ts` → `tenant_domain`). Preview and production URLs feed the
shared `site-config` base-URL helper used by discovery metadata and agent
credentials.

### Database migrations before deploy

The `migrate` job in `deploy-vercel.yml` runs `db:migrate` for the web-app
database before any app deploys, on production runs only. Add `DATABASE_URL`
(the production console database) as a repository secret under GitHub
**Settings > Secrets and variables > Actions**. While it is absent the job logs a
notice and succeeds without touching a database. If it fails, no app is
deployed. See [Database migrations](/operations/migrations) for the baseline
step an existing database needs once.

Stripe webhooks and Inngest run on the backend: point Stripe at
`https://<backend>/api/webhooks/stripe` and sync Inngest with
`https://<backend>/api/inngest`. Sites only send Inngest events.

## Docker

The root `Dockerfile` builds one Next.js app per image, selected with build args
(`APP_DIR`, `APP_PACKAGE`, `PORT`; defaults build `sites/net.alloydb.console` on
8801). Apply database migrations separately and provide runtime variables
through the deployment secret store.

## Documentation sites

If Mintlify hosts `docs-public/` and `docs-internal/` separately, confirm the
internal site's access control before publishing. The `/docs` route every
site serves loads `docs-public/` through the site's fumadocs source rather
than a forked copy.

## Post-deploy checks

On each site: `/status`, `/robots.txt`, `/sitemap.xml`, `/auth.md`,
OAuth/OIDC metadata, JWKS, the MCP server card, and `/mcp` with the intended
authentication state. On the backend: `/login` renders, `/dashboard` redirects
to `/login` when signed out, `/api/admin/*` returns 401 without a session,
and `/mcp` without `?tenant=` returns 400.
